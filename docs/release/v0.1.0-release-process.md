## Release sequence

1. **Dev final validation** — `check_prompts.py`, `validate_research_data.py` on Dev fixtures
2. **Dev commit** — includes `SPEC.md`, updated `AGENTS.md`, thin `.cursor/rules/`, `docs/agents/`
3. **Dev push** — private remote
4. **Public Template synchronization** — copy public surface per extraction checklist (not Dev-only docs, `SPEC.md`, or research outputs)
5. **Verify Public Template exclusions** — confirm root `SPEC.md` is absent; sync `AGENTS.md` without Dev-only session rules
6. **Template validation** — commands in extraction checklist
7. **Template commit**
8. **Template push**
9. **Sample final validation** — strict validate on demo project paths
10. **Sample commit/push** if needed
11. **Tag `v0.1.0`** on the Template commit with synced agent structure and public documentation
12. **GitHub Release** on public Template repository
13. **Post-release verification** — CI green, README/Sample links, no ReSPEC references, no root `SPEC.md` in Public Template

## Tag policy

The `v0.1.0` tag on Public Template must point to a commit that includes:

- Multi-agent structure (`AGENTS.md`, thin `.cursor/rules/`, `docs/agents/README.md`)
- Public Template CI configuration
- No root `SPEC.md` (Dev-only)

If an earlier `v0.1.0` tag exists on an outdated commit, **do not move the tag automatically**.
User actions:

1. Delete the old tag locally and on remote if it was applied incorrectly, **or**
2. Create a new patch release tag after fixing content

Document the chosen approach in the release notes.

**Known prior tag (audit):** `v0.1.0` → `2ab99c07` predates the current agent-structure sync.

- `git tag`

- Tag deletion or retagging if required
